# Abstraction Findings — Agent 3 (Dialogs / Overlays / Menus / Notification UI)

## Finding 1: Real confirmation-dialog base/specialization exists, but lives outside `UI/PlatformConcepts` and bypasses `ModalPresenter`
- File: `Platforms/Windows/ConfirmationDialog.cs` (base, `Options`/`Result`/`ShowAsync`), `Platforms/Windows/CloseConfirmationDialog.cs` (specialization, `ShowAsync`)
- Description: The app already has exactly the base-unit -> specialization shape the project wants (`ConfirmationDialog` generic mechanism + `CloseConfirmationDialog` supplying only its own wording/options — the doc comment on `CloseConfirmationDialog` explicitly compares itself to `DebouncedEntry`/`SearchInputField`). However both types are native WinUI (`Microsoft.UI.Xaml.Controls.ContentDialog`) classes under `Platforms/Windows/`, never routed through `UI/PlatformConcepts/ModalPresenter`, which remains an empty scaffold (`return new ContentView();`). `ModalPresenter`'s own XML doc says the Windows shape should be "a dialog/popup on desktop" but the actual dialog was built independently and the two were never connected. This means the one genuinely reusable dialog mechanism in the codebase does not benefit from (and cannot be swapped by) the neutral `ModalPresenter` abstraction meant to unify overlay presentation across platforms.
- Suggested fix: Fold `ConfirmationDialog`/`CloseConfirmationDialog` into the `ConfirmationBox` -> `ExitConfirmationBox` pattern requested by the task, built on top of (or wired through) `ModalPresenter.Current` so a future mobile bottom-sheet implementation of `ModalPresenter` automatically produces the mobile shape for every confirmation, including this one.

## Finding 2: Tray icon context menu is hand-rolled directly with raw Win32 popup-menu APIs, bypassing `ActionMenu`
- File: `Platforms/Windows/TrayIconNativeHost.cs:128-169` (`ShowContextMenu`, using `CreatePopupMenu`, `AppendMenu`, `TrackPopupMenuEx`, `DestroyMenu`)
- Description: `UI/PlatformConcepts/ActionMenu.cs` exists specifically to be "the closest idiomatic match to a desktop context menu (also used by the tray icon's own right-click menu)" per its own doc comment — but the actual tray right-click menu never uses `ActionMenu` or `MenuFlyout`/`FlyoutBase.ContextFlyout` at all. It instead calls straight into native Win32 (`CreatePopupMenu`/`AppendMenu`/`TrackPopupMenuEx`) built from `TrayIconService.MenuItems`, entirely independent of the `ActionMenu` scaffold whose own comment claims to represent exactly this use case.
- Suggested fix: Either treat the tray menu as an intentionally separate native-only concern (tray icons have no MAUI visual tree) and update `ActionMenu`'s doc comment to stop claiming it backs the tray menu, or — if a shared abstraction is wanted — route both the tray context menu and any future in-app right-click menu (e.g. project card actions) through a single `ActionMenu`-based mechanism so `MenuItems`-style data feeds one presentation path instead of two.

## Finding 3: `RecentNotificationsFlyout` is a fully hand-rolled overlay/backdrop popover, not built on `Drawer` or `ModalPresenter`
- File: `Features/Notifications/Views/RecentNotificationsFlyout.xaml` / `.xaml.cs`; wiring in `Features/Projects/Views/MainWindowPage.xaml` (`NotificationsFlyout`, `NotificationsBackdrop`) and `Features/Projects/Views/MainWindowPage.xaml.cs:27-54` (`OpenNotificationsFlyout`, `SetNotificationsFlyoutVisible`, `OnNotificationsFlyoutCloseRequested`, `OnNotificationsBackdropTapped`)
- Description: The notifications popover is a `ContentView` manually toggled via `IsVisible`, paired with a separate, manually-toggled full-page transparent `BoxView` backdrop for outside-click dismissal, plus a hand-wired `CloseRequested` event for its own X button. This is exactly the "secondary/contextual panel" concept `UI/PlatformConcepts/Drawer.cs` exists for (it is even called a "flyout" in both places), yet `Drawer.Current` is never used — it remains an unused `ContentView()` scaffold. The show/hide + backdrop + dismiss-button trio duplicates logic that any second popover (e.g. a future user/account menu) would have to hand-roll again from scratch.
- Suggested fix: Promote the visible/backdrop/dismiss trio into a reusable `PopoverPanel`-style base unit (or wire it directly through `Drawer`), so `RecentNotificationsFlyout` becomes a thin specialization the same way `CloseConfirmationDialog` specializes `ConfirmationDialog`.

## Finding 4: `ModalPresenter`, `Drawer`, and `ActionMenu` remain unused scaffolds despite three concrete real-world use cases already existing in the codebase
- File: `UI/PlatformConcepts/ModalPresenter.cs:13-28`, `UI/PlatformConcepts/Drawer.cs:12-27`, `UI/PlatformConcepts/ActionMenu.cs:13-30`
- Description: Quoting the current scaffold state exactly:
  - `ModalPresenter.CreateDialog()`: `// Windows "Dialog" stand-in: a centered content container. TODO: replace with a real modal ContentPage pushed via PushModalAsync, or Popup, once a concrete dialog use case (e.g. confirm/settings) is implemented.` `return new ContentView();`
  - `Drawer.CreateFlyout()`: `// Windows "Flyout" stand-in: a lightweight content container representing the flyout panel's content slot. TODO: wire this up to an actual FlyoutPage.Flyout / Shell flyout once a concrete secondary-panel use case is implemented.` `return new ContentView();`
  - `ActionMenu.CreateContextMenu()`: `// Windows "ContextMenu" stand-in: a lightweight content container standing in for the element that would carry a MenuFlyout via FlyoutBase.ContextFlyout. TODO: attach a real MenuFlyout with MenuFlyoutItem entries once a concrete action-list use case (e.g. project card right-click actions) is implemented.` `return new ContentView();`
  Each TODO explicitly names a "concrete use case" as the trigger for implementation — but Findings 1–3 show those concrete use cases (a real confirmation dialog, a real context menu, a real flyout/drawer) already exist in the app today, built independently instead of triggering these scaffolds' completion.
- Suggested fix: Treat Findings 1–3 as the "concrete use case" each TODO is waiting on, and implement `ModalPresenter`/`Drawer`/`ActionMenu` for real using those existing call sites as the first consumers, rather than waiting for new features to justify them.

## Finding 5: Destructive "clear session cookie" action has no confirmation at all (missing `ConfirmationBox` call site)
- File: `Features/Settings/ViewModels/SettingsViewModel.cs:264-268` (`ClearSessionCookieAsync`)
- Description: `ClearSessionCookieAsync` is documented as "Deletes the stored session so the app goes back to anonymous scraping" and executes immediately on command invocation with no user confirmation step, unlike the X-button close flow which does get a confirmation dialog (`CloseConfirmationDialog`). This is not itself a duplicated/hand-rolled abstraction, but it is a second real destructive-action site that a future `ConfirmationBox` base unit should cover — worth tracking alongside the exit-confirmation migration so the new unit is designed for more than one call site from the start.
- Suggested fix: Once `ConfirmationBox`/`ExitConfirmationBox` exists (per Finding 1), add a second specialization (e.g. `ClearSessionConfirmationBox`) or a generic parameterized usage for this command, rather than leaving it as a silent one-click destructive action.
