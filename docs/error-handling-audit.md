## Tool design

`tools/ErrorHandlingAudit` parses every `*.cs` file (excluding `bin`/`obj`/`MostaqlK.UITests`/`tools`)
with a plain `CSharpSyntaxTree` — no `MSBuildWorkspace` project load, which was judged fragile/slow
for this environment and unnecessary for the four purely-structural rules in
`errors-handling.md`. Four rules: **A** factory-bypass construction, **B** swallowed catches,
**C** unread `ExternalMessage`/`FixMessage`, **D** missing `[ErrorCode]`/`[ErrorOutcome]` tagging.
Tuned against `tools/ErrorHandlingAudit/Fixtures/*.cs` (2 compliant + 2 violating per rule, 8 total)
until it reported **0 false positives / 0 false negatives** — verified on the first tuning pass for
rules A/B/C; Rule D initially over/under-fired until the fixture for the "Result.Err arm" shape was
rewritten to use a real `Result<T>.Err(...)` call (see fixture file history), then also passed
0/0. Rule B was additionally widened twice while validating against the *real* codebase (see
"Manual classification" below): once to exempt `catch` blocks that `return Result<T>.Err(...)`
(propagation via `Result`, not a swallow) and once to exempt catches whose enclosing method already
carries an explicit `[ErrorOutcome]` tag (documented-deliberate swallow) — both re-verified against
the fixture suite afterwards with no regression (still 0/0, 10/10 expected violations).

Invocation: `dotnet run --project tools/ErrorHandlingAudit -- <rootDir> [--out <file.md>] [--include-fixtures]`
(run from the repo root with `<rootDir>` = `.`).
